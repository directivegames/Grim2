# 15 → 16

Version 16 separates **detaching** a node from the scene graph from **destroying**
it. In 15, `remove()` / `removeFromParent()` did both: they detached the object
*and* ran `endPlay` (and, for world roots during play, disposed GPU resources).
That made reparenting a live node falsely end and restart play, so projects
worked around it with hand-rolled detach helpers.

In 16 the two operations are distinct:

| Intent | API | Runs `endPlay`? | Disposes GPU? |
|---|---|---|---|
| Reparent / temporarily detach | `remove()`, `removeFromParent()` | No | No |
| Tear down for good | `destroy()` | Yes | While playing (or `forceDispose`) |
| Editor helper (`ArrowHelper`, light/camera helpers) | `removeFromParent()` then `helper.dispose()` | No | Via `helper.dispose()` |

Work through the sections in order. Section 1 is the one that touches the most
code; sections 4–8 are behavioural changes that only bite specific patterns.

## 1. `remove()` / `removeFromParent()` no longer tear down — use `destroy()`

Every call site that meant "get rid of this node" must now call `destroy()`.
A call site that meant "move this node somewhere else" stays as it is.

This is a silent break: the object still disappears from the graph, so the bug
does not show up as a compile error. Symptoms are a node that keeps ticking
after removal, an `endPlay` override that never runs, growing GPU memory during
play, and (in the editor) `onEditorRemoveFromWorld` never firing.

`parent.remove(child)` is the same detach as `child.removeFromParent()`. If the
child is being deleted, call `child.destroy()` — do not leave it as
`parent.remove(child)`.

```ts
// Before (15): remove / removeFromParent / parent.remove ended play and disposed
this.projectile.removeFromParent();
world.remove(enemy);
parent.remove(duplicateTrigger);

// After (16): destroy() is teardown
this.projectile.destroy();
enemy.destroy();
duplicateTrigger.destroy();
```

Audit each hit rather than replacing blindly — the pooling and reparenting
cases below are meant to keep `removeFromParent()`. Editor helpers stay on the
`removeFromParent()` + `dispose()` pair in section 2.

## 2. `destroy()` exists on every `Object3D` and takes an options bag

`destroy()` used to be a `SceneNode` method that just called
`removeFromParent()`. It is now declared on `THREE.Object3D` and performs a full
teardown, in this order: `endPlay` (if playing) → editor remove hook → dispose
GPU (if playing, or `forceDispose`) → detach from parent.

Dispose walks the subtree. `SceneNode` runs `dispose(disposer)`. `Mesh` /
`Line` / similar objects free geometry and materials that are not cache-owned
(loaded GLTF originals stay). A privately allocated
`new THREE.Mesh(new THREE.BoxGeometry(), …)` is therefore freed by `destroy()`
during play — do not add a second `geometry.dispose()` after that.

Dispose is skipped when the world is not playing, so editor deletes of authored
nodes stay undo-restorable. `forceDispose` is only for teardown **outside play**:

- Use it when replacing privately allocated meshes or groups in the editor or
  before `beginPlay` (greybox props, debug overlays you built yourself).
- Do not use it when deleting authored scene or prefab nodes — undo must keep
  their GPU.

```ts
// After (16)
node.destroy();                       // endPlay, editor hook, dispose if playing, detach
node.destroy({ forceDispose: true }); // also dispose when not playing
```

Editor helpers are a third pattern. `ArrowHelper` line/cone geometries are
shared module objects until you clone them; `PointLightHelper` /
`CameraHelper` own per-instance GPU. Leave their teardown as
`removeFromParent()` then `helper.dispose()` (clone both `ArrowHelper`
geometries right after `new`). Do not rewrite those to `destroy()`.

```ts
// After (16): editor helper — unchanged from 15
this.editorArrow.removeFromParent();
this.editorArrow.dispose();
```

`destroy()` is a Genesys method on `THREE.Object3D`. Files that import only
`three` still compile against the runtime patch once the game has loaded
`@gnsx/genesys.js`; do not add a side-effect engine import just to call
`destroy()`.

## 3. `world.remove()` is detach-only; `removeActor(s)` shims route to `destroy()`

`world.remove(node)` no longer ends play, fires editor hooks, or disposes. Use
`node.destroy()` to delete a world root.

`world.removeActor(node)` and `world.removeActors(...nodes)` still exist as
**deprecated** compatibility shims and now call `destroy()` internally, so their
behaviour is unchanged from 15. They are still deprecated: the project lint
preset sets `@typescript-eslint/no-deprecated` to error, so `pnpm lint` will
flag them. Prefer `node.destroy()`.

```ts
// Before (15)
world.remove(pickup);
world.removeActor(pickup);

// After (16)
pickup.destroy();
```

## 4. Reparenting keeps play state — drop custom detach helpers

`add()` and `attach()` now recognise a reparent and leave an already-playing
node Playing. `beginPlay` fires only on a node that has not started yet, so
moving a live node between parents no longer restarts it.

If your project wrote a helper to avoid the old double-`endPlay` (commonly named
something like `detachFromParent`, wrapping `object.parent?.remove(object)`),
that workaround is no longer needed for reparenting — `add()` detaches from the
previous parent for you. Keep such a helper only where you deliberately want a
node parked outside the graph without tearing it down.

```ts
// Before (15): detach through a helper, then re-add, to dodge double endPlay
detachFromParent(this.lockOnMarker);
newTarget.add(this.lockOnMarker);

// After (16): a plain reparent preserves Playing
newTarget.add(this.lockOnMarker);
```

Overrides of `beginPlay` / `endPlay` that used to run on every reparent now run
once per real play transition. Move any per-attach work (recomputing an offset,
re-reading the parent) out of those hooks and into the code that reparents.

Also drop play-state repair that exists only because detach used to end play:
`resetPlayStateForWorldTransition`, `endPlay` + `beginPlay` "reenter" helpers,
and comments about camera attach / detach breaking the next `add()`. After a
plain reparent the node is still Playing. An `Ended` node cannot be revived —
create a fresh instance instead (section 5). `resetPlayStateForWorldTransition`
is gone in 16 (section 10).

## 5. An `Ended` node cannot be re-added; a `Playing` node cannot move to a non-playing parent

Two new guards refuse the operation and log instead of silently corrupting play
state:

- Adding a node whose play state is `Ended` (that is, a node you already
  `destroy()`ed or ended) is rejected.
- Moving a `Playing` node under a parent that is not playing is rejected.

This breaks the pool-by-detaching pattern if the pool used to tear nodes down.
Park reused instances instead of destroying them, or destroy and create a fresh
instance on the next spawn.

```ts
// Before (15): detach into a pool, re-add later
node.removeFromParent();
this.pool.push(node);
// ...later
world.add(node);

// After (16), option A — park it: still parented and Playing, just not visible
node.visible = false;
node.setTickEnabled(false);
this.pool.push(node);
// ...later
node.visible = true;
node.setTickEnabled(true);

// After (16), option B — destroy and respawn a fresh instance
node.destroy();
// ...later
world.add(MyNode.create({ name: 'Spawned' }));
```

Check `getPlayState()` / `isPlayEnded()` when a cached reference might already be
torn down.

## 6. `Object3D.insert(object, index?)` for ordered parenting

`add()` always appends. `insert()` parents a child at a specific sibling index
and runs the same enter lifecycle, so use it instead of splicing `children` by
hand — a manual splice skips `beginPlay` and the editor add hook. Omitting
`index`, or passing an out-of-range one, appends.

```ts
// Before (15): manual splice, no lifecycle
child.removeFromParent();
child.parent = parent;
parent.children.splice(2, 0, child);

// After (16)
parent.insert(child, 2);
```

## 7. `getWorld()` on any `Object3D`

`getWorld()` is now declared on `THREE.Object3D`, not just `SceneNode`, so a
plain `Group` or `Mesh` in the graph can resolve its owning `World`. A
`SceneNode` caches its world from `beginPlay` until `endPlay`, so while playing
the result no longer depends on walking parents — reparenting a live node cannot
make `getWorld()` momentarily return `null`.

## 8. `world.disposeSubtreeResources()` removed

`World.disposeSubtreeResources(root)` is gone. During play, `destroy()` already
walks the subtree and frees GPU (section 2). Outside play, `forceDispose` is the
replacement for the old dispose-then-remove pair.

```ts
// Before (15)
world.disposeSubtreeResources(node);
node.removeFromParent();

// After (16)
node.destroy({ forceDispose: true });
```

To free resources your own class allocated, override
`dispose(disposer: ENGINE.IDisposer)` on your `SceneNode` — `destroy()` calls it
for every node in the subtree.

## 9. `NetWorld` is no longer `Playable` — use the world notifications

`NetWorld` is created, ticked, and destroyed by the game loop, and it outlives every
`World` it serves. `Playable` models a single terminal lifetime, which never fit:
`endPlay()` had to reset the state straight back to `NotStarted` so the next world
could start, so `Ended` was unreachable and `getPlayState()` reported something
misleading.

In 16 it stops being `Playable`. `beginPlay`, `endPlay`, `isPlaying`, `isPlayEnded`,
`getPlayState`, `resetPlayStateForWorldTransition`, and `detachFromWorld` are gone
from `NetWorld`. Two plain notifications replace them, both idempotent, so a repeated
or out-of-order call is a no-op rather than a failed assertion:

- `onWorldBeginPlay(): Promise<boolean>` — awaited by the game loop after the world
  begins play and `GameSessionInfo` exists.
- `onWorldEndPlay(): boolean` — called by `World.endPlay()` as the world leaves play.

`onLocalWorldBeganPlay()` folded into `onWorldBeginPlay()`. `onLocalLevelLoaded()` is
unchanged.

Most projects only need this section if they hand-rolled a reset before a cold level
reload. That workaround existed because `World.endPlay()` left the shared `NetWorld`
in a state the next `World.beginPlay()` rejected. It is no longer needed — delete it.

```ts
// Before (15): reset the shared NetWorld before reloading the level
const netWorld = world?.netWorld;
if (netWorld?.isPlaying()) {
  netWorld.endPlay();
} else if (netWorld?.isPlayEnded()) {
  netWorld.resetPlayStateForWorldTransition();
}
void gameLoop.openLevel(activePath);

// After (16): the notifications rebind for each world on their own
void gameLoop.openLevel(activePath);
```

A custom `NetWorld` subclass overrides the notifications instead, calling `super`
first and skipping its own work when `super` reports the call was a no-op.

```ts
// Before (15)
public override beginPlay(): boolean {
  if (!super.beginPlay()) return false;
  this.bindMyThing();
  return true;
}

public override onLocalWorldBeganPlay(): void {
  this.ackLevelLoaded();
}

// After (16)
public override async onWorldBeginPlay(): Promise<boolean> {
  if (!await super.onWorldBeginPlay()) return false;
  this.bindMyThing();
  this.ackLevelLoaded();
  return true;
}
```

`Playable` itself still exists and is unchanged for single-lifetime systems.

## 10. `openLevel` is always a cold load — no node crosses a `World` boundary

`openLevel` used to default to carrying `PlayerController` roots into the next
world (`preserveRoots: true`). That produced a duplicate local controller in
single-player (the preserved instance plus the one the new `GameMode` spawns)
and left `Ended` unenforceable: preserved nodes were reset to `NotStarted` so
`beginPlay` could run again.

In 16 every `openLevel` tears the current world down completely. The new world
spawns a fresh controller and pawn from its `GameMode` factory. There is no
API for moving a live node between worlds.

Removed:

- `OpenLevelOptions` / `preserveRoots`
- `GameLoop.collectRootsToPreserveAcrossLevelTransition` (and the detach / reinsert helpers)
- `World.detachRootsPreservingAcrossLevelTransition`
- `resetPlayStateForWorldTransition` on `Playable`, `SceneNode`, and `PlayerController`

`Ended` is terminal. If you need the same gameplay object again, create a new
instance — do not reset play state and re-add.

```ts
// Before (15): skip carrying the old PlayerController across a reload
void gameLoop.openLevel(activePath, { preserveRoots: false });
void gameLoop.reloadInitialLevel({ preserveRoots: false });
weapon.resetPlayStateForWorldTransition();
parent.add(weapon);

// After (16): every openLevel is cold; recreate instead of resetting
void gameLoop.openLevel(activePath);
void gameLoop.reloadInitialLevel();
weapon.destroy();
parent.add(MyWeapon.create());
```

Call sites that already passed `{ preserveRoots: false }` just drop the
argument. Call sites that relied on the `true` default (including client
`LOAD_LEVEL` handling) now get a full teardown; that is the intended model.

## 11. Server level changes are teardown plus a fresh join

A dedicated-server `openLevel` destroys the old world (and every player node
in it) and then admits each still-connected client through the **new** world's
`GameMode` factory — the same path as a first-time join (`handleServerPlayerJoin`
with empty join params, then `LOAD_LEVEL`). Connections stay on `NetWorld`;
controllers, pawns, and `PlayerInfo` do not.

Removed:

- `GameMode.cleanupPlayersForLevelTransition`
- `GameMode.respawnControllerForTransition`
- `GameMode.migratePlayerInfo`
- `ServerAuthorityNetWorld` `preservedClientIds`

Same-level disconnect/rejoin is unchanged: `identityToken` snapshots on the
**current** `GameMode`, and `onClientLevelLoaded` still links `PlayerInfo` when
the controller has none. Do not use that path to carry score or loadout across
a world change — persist that in your own game code if you need it.

```ts
// Before (15): GameMode kept PlayerInfo and respawned a bare controller
gameMode.cleanupPlayersForLevelTransition();
await gameMode.respawnControllerForTransition(clientId);

// After (16): delete those calls. openLevel already destroys player nodes;
// NetWorld re-admits connectedClients when the new level is ready.
void gameLoop.openLevel(nextPath);
```

## 12. Custom transports: `ReplicationPacket`/`ReplicationAck` split into four packet/ack pairs

Only relevant to code that implements a custom `IGameSession` transport or reads/sends raw
replication packets directly — not to game code that only uses `MultiplayerSpawner` or
`replicated` nodes.

The monolithic `ReplicationPacket`/`ReplicationAck` frame is replaced by four independent
packet/ack pairs, one per replication concern:

| Concern | Packet (server → client) | Ack (client → server) |
| --- | --- | --- |
| Spawner journal ops | `SpawnerReplicationPacket` | `SpawnerReplicationAck` |
| Entity teardown | `TombstoneReplicationPacket` | `TombstoneReplicationAck` |
| Entity channel establish | `EntityEstablishReplicationPacket` | `EntityEstablishReplicationAck` |
| Entity delta update | `EntityUpdateReplicationPacket` | `EntityUpdateReplicationAck` |

`EntityUpdateType` / `EntityAckType` (the `Establish`/`Update` discriminant tags) are removed —
each concern now has its own packet type instead of a tagged union sharing one frame.
`EntityUpdate` / `EntityAck` are replaced by `EntityEstablishEntry` / `EntityUpdateEntry` (the
packet they arrived on already says which kind they are, so no tag is needed). The earlier
`SpawnData` type from the previous release is `EntityBinding` (bind only) plus
`ChannelEstablishData` (bind + owner + initial state) — unchanged in this step, still current.

`IGameSession` gains matching delegates and send methods for each pair, replacing the single
pair that used to cover everything:

| Before | After |
| --- | --- |
| `onReplicationPacketReceived` | `onSpawnerReplicationReceived`, `onTombstoneReplicationReceived`, `onEntityEstablishReplicationReceived`, `onEntityUpdateReplicationReceived` |
| `onReplicationAckReceived` | `onSpawnerReplicationAckReceived`, `onTombstoneReplicationAckReceived`, `onEntityEstablishReplicationAckReceived`, `onEntityUpdateReplicationAckReceived` |
| `sendReplicationPacket()` | `sendSpawnerReplicationPacket()`, `sendTombstoneReplicationPacket()`, `sendEntityEstablishReplicationPacket()`, `sendEntityUpdateReplicationPacket()` |
| `sendReplicationAck()` | `sendSpawnerReplicationAck()`, `sendTombstoneReplicationAck()`, `sendEntityEstablishReplicationAck()`, `sendEntityUpdateReplicationAck()` |

Entity teardown is now always its own `TombstoneReplicationPacket`, sent independently of
establish/update traffic, and fans out to already-connected clients as well as late joiners.
`EntityTombstone` also gained a required `netId: NetId` field on both its `'scene'` and
`'spawn'` variants (previously it only carried enough to locate the node by path, which broke
if the node had been reparented since spawn) — a custom transport constructing or consuming
`EntityTombstone` values directly needs to populate/read `netId` too.

```ts
// Before: one frame, discriminated by updateType
session.onReplicationPacketReceived.add((packet) => {
  for (const spawner of packet.spawners ?? []) { /* ... */ }
  for (const tombstone of packet.tombstones ?? []) { /* ... */ }
  for (const entity of packet.entities) {
    if (entity.updateType === EntityUpdateType.Establish) { /* entity.data: ChannelEstablishData */ }
    else { /* entity.data: UpdateData */ }
  }
});

// After: one handler per concern
session.onSpawnerReplicationReceived.add((packet) => { for (const s of packet.spawners) { /* ... */ } });
session.onTombstoneReplicationReceived.add((packet) => { for (const t of packet.tombstones) { /* ... */ } });
session.onEntityEstablishReplicationReceived.add((packet) => { for (const e of packet.entities) { /* e.data: ChannelEstablishData */ } });
session.onEntityUpdateReplicationReceived.add((packet) => { for (const e of packet.entities) { /* e.data: UpdateData */ } });
```

Reference implementation: `multiplayer/interface.ts`, `multiplayer/implementations/NetworkProtocol.ts`.

## Verify

Search the project's TypeScript for:

```text
removeFromParent\(
\.remove\(
parent\.remove\(|world\.remove\(|removeActor\(|removeActors\(
disposeSubtreeResources
detachFromParent
children\.splice
resetPlayStateForWorldTransition
preserveRoots
openLevel\(
reloadInitialLevel
netWorld\.|extends ENGINE\.(NetWorld|StandaloneNetWorld|ClientNetWorld|ServerAuthorityNetWorld)
onLocalWorldBeganPlay
ReplicationPacket|ReplicationAck\b
EntityUpdateType|EntityAckType
\bEntityUpdate\b|\bEntityAck\b
onReplicationPacketReceived|onReplicationAckReceived
sendReplicationPacket\(|sendReplicationAck\(
```

For any `ReplicationPacket`/`ReplicationAck`/`EntityUpdateType`/`EntityAckType` hit, apply
section 12 — this only fires in a hand-rolled `IGameSession` transport, not in normal
`MultiplayerSpawner`/`replicated`-node gameplay code.

For every `remove` / `removeFromParent` / `parent.remove` hit, decide which
intent it had and act accordingly:

- The object is being deleted, pooled-by-teardown, replaced, or cleaned up in a
  `dispose` / `cleanup*` / `destroy` method → `destroy()` (add `forceDispose`
  only when that cleanup can run outside play on privately allocated GPU).
- The object is moving to another parent, or being parked for later reuse →
  leave it as `remove()` / `removeFromParent()`.
- An editor helper (`ArrowHelper`, `PointLightHelper`, `CameraHelper`) in
  `onEditorRemoveFromWorld` → leave `removeFromParent()` + `helper.dispose()`.

Treat `.remove(` carefully: it also matches DOM `Element.remove()`, `Map` /
`Set` / `Delegate` removals, and `classList.remove`, which are unrelated.

For `beginPlay` / `endPlay` / `resetPlayStateForWorldTransition` hits:

- Per-attach work inside those hooks (re-read parent, recompute an offset) →
  move it to the reparent site.
- `endPlay` + `beginPlay` or `resetPlayStateForWorldTransition` immediately
  after a detach / `add()` → drop it. If `isPlayEnded()` is true, create a
  fresh instance instead of resetting.

For `netWorld.` and `NetWorld` subclass hits, apply section 9: play-state calls on a
`NetWorld` no longer exist, and a pre-reload reset can simply be deleted.

Then:

1. Run `pnpm build`, then `pnpm lint`.
2. Play, stop, and replay twice. Watch for nodes that still tick after being
   removed, `endPlay` overrides that never fire, and duplicated spawns.
3. Exercise reparenting (weapon swaps, lock-on markers, attach points) and
   confirm state survives the move rather than resetting.
4. Exercise pooled spawners across a full reset to catch rejected re-adds of
   `Ended` nodes.
